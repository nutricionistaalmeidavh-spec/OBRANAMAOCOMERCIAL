# F12 — Central RH Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Make employee, payroll, timekeeping, benefits and PPE data authoritative in the LAN server for central-active installations while preserving existing Desktop behavior and permissions.

**Architecture:** Extend the central schema for RH, port payroll/time domain transactions to server-side services, route existing Desktop APIs through an operational-source adapter, and gate activation behind migration state. No second RH UI or Cloud identity model is introduced.

**Tech Stack:** Node `node:sqlite`, Electron/CommonJS, Vitest, node:test.

**Spec:** `docs/superpowers/specs/2026-09-30-centralized-modules-sync-f8-f12-design.md`

## Global Constraints

- RH authorization is enforced server-side using the current Cloud/LAN member/module snapshot.
- Local mode remains unchanged.
- Central-active RH never falls back to local SQLite on server failure.
- Composite payroll/time operations stay atomic in the server process.
- Existing local RH data => `migration-required`; F17 migrates it.
- No document-byte/cloud-storage migration is introduced here.

## Review Focus

- Confirming a payroll period twice must be rejected exactly once and never duplicate payment.
- Employee/cargo/benefit relations must stay company-scoped.
- A user without RH authorization must receive `403` even if UI calls the endpoint manually.
- Time/payroll operations interrupted by network failure must not leave partial central state.
- A second LAN client must immediately read the same employee/payroll/time state after commit.
