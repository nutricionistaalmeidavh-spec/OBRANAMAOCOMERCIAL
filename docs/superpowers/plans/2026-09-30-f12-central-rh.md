# F12 — Central RH Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Make employee, payroll, timekeeping, benefits and PPE data authoritative in the LAN server for central-active installations while preserving existing Desktop behavior and permissions.

**Architecture:** Extend the central schema for RH, port payroll/time data transactions to server-side services, route existing Desktop APIs through an operational-source adapter, and keep PDF/file rendering local as a derived output rather than pretending document storage has been centralized. No second RH UI or Cloud identity model is introduced.

**Tech Stack:** Node `node:sqlite`, Electron/CommonJS, Vitest, node:test.

**Spec:** `docs/superpowers/specs/2026-09-30-centralized-modules-sync-f8-f12-design.md`

## Global Constraints

- RH authorization is enforced server-side using the current Cloud/LAN member/module snapshot.
- Local mode remains unchanged.
- Central-active RH never falls back to local SQLite on server failure.
- Composite payroll/time data operations stay atomic in the server process.
- Existing local RH data => `migration-required`; F17 migrates it.
- Document bytes/storage are not centralized here. Generated PDFs remain local derived files and must not be presented as shared LAN/Cloud documents.

## Review Focus

- Confirming a payroll period twice must be rejected exactly once and never duplicate payment.
- Employee/cargo/benefit relations must stay company-scoped, including `cargo_beneficios`.
- A user without RH authorization must receive `403` even if UI calls the endpoint manually.
- Time/payroll operations interrupted by network failure must not leave partial central state.
- Local PDF generation in central RH mode must use central employee/time data without creating a false second authoritative RH copy.
